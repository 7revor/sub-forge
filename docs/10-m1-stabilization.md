# 10 · M1 稳定化与订阅更新一致性

日期：2026-10-28。基线：`0ad35de`。本轮在 `codex/m1-stabilization` 中修复；未合并、未部署。

## 1. 模板更新为什么需要资源版本

订阅跟随最新模板是预期行为，不需要用户逐个确认。服务端每次生成主订阅时，使用最新模板与个人覆盖合并；客户端下次刷新主订阅后使用新配置。

问题在于客户端并非一次下载完整配置包，而是分别请求：

| 请求 | 内容 | 刷新时机 |
| --- | --- | --- |
| `/sub/:token` | 策略组、规则顺序、节点与规则资源的引用 | 主订阅刷新 |
| `/p/:token/:key` | 节点 provider 内容，包括可能注入的前置引用 | provider 自己的更新周期 |
| `/r/:token/:key` | 转换后的规则集内容 | 规则 provider 自己的更新周期 |

例如，客户端现有主配置只有“旧前置”组，模板发布后该组改名为“新前置”。如果旧 provider 地址直接返回新渲染的内容，节点里的 `dialer-proxy` 会指向客户端尚未加载的“新前置”。规则集也类似：旧主配置可能仍引用 domain 桶，更新后的规则却被拆入 CIDR 或 classical 桶。直接把所有资源地址背后的内容替换成最新结果，就会混合两套不兼容配置。

这和“模板自动同步”不冲突：自动同步描述服务端如何派生配置；版本一致性保证客户端分批下载时，拿到彼此兼容的主配置和资源。

## 2. 本轮实现的更新策略

1. **跟随最新**：模板发布后，下次请求主订阅自动生成新版本；个人覆盖按组 / 规则的稳定 ID 合并。锁定模板版本的订阅继续使用所锁定的版本。
2. **主配置与资源使用同一结构版本**：provider、规则集地址都带 `v`，并保留输出平台。请求旧版本只能取得该版本的资源，不会偷偷改为最新结构。
3. **兼容的远程内容继续独立刷新**：远程节点和规则快照本身不进入结构版本指纹。只要渲染后的主配置结构不变，例如已有 provider 增减普通节点、已有 domain 桶替换域名，原地址仍可刷新内容。
4. **结构变化整套切换**：模板 / 个人配置 / 依赖文档变化，或远程更新导致包装组、规则分桶等主配置结构变化，会得到新结构版本。旧客户端继续使用保留的旧资源；刷新主订阅后切到新版本。
5. **失败时整套回退**：渲染失败返回最近一次成功主配置，该配置所引用的资源也仍按相同版本读取。恢复到缓存中的旧配置后，该配置会重新成为最近成功结果。

结构版本使用 SHA-256 的前 32 个十六进制字符。provider 地址里的 `h` 是内容摘要，仅用于主配置刷新时改变客户端资源缓存地址，不代表新的结构版本。

版本存储按 Profile 与输出目标隔离，加密保存最近 32 个结构版本。同一结构下的远程内容刷新只更新该条记录，不额外占用版本名额。超过保留范围的资源地址返回 404，并提示刷新主订阅。删除 Profile 会清理其版本；撤销订阅链接或禁用所属用户后，历史资源同样不可访问。

### 升级边界

- 数据库自动迁移到 v4，新增加密的结构版本存储；v1 / v2 快照的 URL 与错误信息迁移为加密字段，查询改用 HMAC 索引，并清理数据库空闲页与 WAL 中的旧明文。
- 升级前 provider 地址中的 8 位内容摘要，只能从原库保留的最近成功结果恢复；旧地址没有平台参数时，会在已保存的平台结果中匹配。
- 升级前规则地址没有版本号，无法从地址反推历史配置。升级后应让现有客户端刷新一次主订阅，取得完整的版本化地址。
- 版本保留不能代替客户端刷新：发生结构变化后，仍使用旧主配置的客户端会保留旧资源内容。远程规则的二进制透传地址（例如 mrs）仍由上游维护，本轮不改变其透传方式。

## 3. 修复范围

| 问题 | 修复与保护 |
| --- | --- |
| 禁用用户后订阅仍可使用 | `/sub`、`/p`、`/r` 统一校验所属用户状态；重新启用后可恢复 |
| 快照地址与错误中可能残留订阅凭据 | URL、错误、正文加密；URL 用 HMAC 查询；旧库迁移并检查文件中无测试明文秘密 |
| 普通动态前置组筛空后可能直连 | 默认输出 `empty-fallback: REJECT`；明确选择直连时才使用 `COMPATIBLE` |
| 代理链检测未覆盖真实组成员 | 纳入 include-all、filter、exclude-filter、exclude-type、复制节点；provider override 按内核优先级处理；缺失前置阻止发布 |
| 主配置与节点 / 规则资源错配 | 使用上述结构版本与完整失败回退策略 |
| 删除依赖破坏历史模板或其他用户配置 | 检查全部保留模板版本、共享规则的跨用户引用；不向删除者泄露其他用户的私有文档名称 |
| 规则转换丢失或扩大 `no-resolve` / `src` 的作用 | 保留单条参数；CIDR 按连续参数片段分组并保持顺序；不同引用选项使用独立资源键；规则包参数覆盖 classical 中的目标 IP 规则 |
| Profile 的错误 YAML 可误保存或切页丢失 | 保存、步骤跳转与来源切换受有效性约束；分区、侧栏、浏览器前后退可拦截；支持修正与明确放弃；注册页面离开提醒 |
| YAML 改模板组名导致个人覆盖失联 | 导出 YAML 用注释保留组 / 规则 ID；修改名称与规则内容仍保留 ID；复制同 ID 报错。外部无 ID 注释的 YAML 仍按名称 / 匹配项识别 |
| Docker 完整测试缺前端依赖 | 安装依赖前复制 web 包声明；排除 `.Codex` 工作树进入构建上下文 |

`no-resolve` 与 `src` 的含义依据 [mihomo 路由规则文档](https://wiki.metacubex.one/config/rules/)；实际 DNS 查询次数和来源 / 目标 IP 匹配另有内核运行时验证。

使用内置浏览器、独立回环地址服务、内存数据库与虚构测试账号，不使用真实订阅。以下场景通过：

1. 先修改有效基础设置，再输入无效 YAML：文本保留，保存和来源切换禁用，分区导航被拦截；选择留下后文本仍在。
2. 修复 YAML 后保存并刷新：`mode: global` 实际保存成功。
3. 没有其他有效改动时，仅输入无效 YAML：显示未保存而不是已保存；侧栏离开被拦截，明确放弃后正常离开。
4. 新建向导：无效 YAML 阻止下一步、跳过和步骤导航；浏览器后退被拦截；放弃无效文本后恢复，并完成七步向导、预览和创建。
5. 模板 YAML 中将“原组名”改成“新组名”、替换域名后发布 v2：组 ID `g` 与规则 ID `r` 保留；原 Profile 的个人 `REJECT` 成员仍在，新域名与新组名生效，渲染零错误 / 告警。
6. 模板列表明确说明客户端下次刷新主订阅时采用新模板；本轮浏览器控制台无错误 / 告警。

服务退出时再次检查内存数据导出，确认保存结果与页面一致。验收页面、临时服务、端口和测试容器均已关闭。页面刷新 / 关闭时的系统原生离开弹窗未单独验收；本轮已实测 SPA 导航和浏览器后退。Surge 输出仍属于 M2，未计入通过。
